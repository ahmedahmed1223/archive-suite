# V1-210D — قبول Windows (وضع Docker، online): مُغلق

## حدود النطاق — اقرأ أولًا

التحقق أدناه جرى على منصة **`windows-10-11-docker`** (حالتها `conditional` في
`infra/platform/compatibility.v1.json`)، وهو ما سجّله المانفست فعليًا
(`"platform": "windows-10-11-docker"`).

**لا يدّعي هذا البند أي دعم لـ`windows-native`** — تلك المنصة تبقى `planned`
في العقد، ومسار Native نفسه غير مُنفَّذ (`doctor --mode=native` يرفض التشغيل،
راجع `docs/platform-parity.md`). الإغلاق هنا يتبع سابقة V1-211D التي أُغلقت
عبر Docker بقرار موثَّق في 2026-07-22، وبمعيار أعلى منها (دورة إصدار موقَّع
كاملة بدل تشغيل اختبارات فقط).

عوائق قبول clean-host الخارجية الباقية مسجّلة في
[`docs/ops/acceptance-clean-host-blockers.md`](../../ops/acceptance-clean-host-blockers.md).

## النتيجة

دورة القبول الكاملة نجحت فعليًا على Windows 11 حقيقي (لا VM، لا محاكاة):

**تثبيت موقَّع (online) → تحديث (update) → تراجع (rollback)** — الثلاثة نجحت
بالتسلسل، بصور Docker حقيقية موسومة بـ`@sha256:` ومُتحقَّقة، على مكدس معزول
تمامًا عن بيئة التطوير الحية (`git worktree` + شبكة/منافذ/أحجام مستقلة، صفر
تصادم مؤكَّد بـ`docker ps`/`docker volume ls` قبل وبعد).

هذه **أول مرة في تاريخ هذا المستودع** يعمل فيها مسار الإصدار الموقَّع
(`install --config=`/`update`/`rollback`) فعليًا من البداية للنهاية — لم يكن
مُختبَرًا من قبل، والدليل على ذلك: احتوى على **خمسة عيوب حقيقية** منعته من
العمل إطلاقًا، اكتُشفت وأُصلحت جميعها أثناء هذا القبول.

|---|---|---|---|

| 2 | حجم Postgres مُثبَّت على `/var/lib/postgresql/data` | يتعارض مع اصطلاح PG18+ الفعلي، postgres يرفض الإقلاع | `docker-compose.release.yml` — تصحيح المسار إلى `/var/lib/postgresql` (مطابق لما تستخدمه `docker-compose.yml` الحي أصلًا) |
| 3 | `ADMIN_EMAIL`/`ADMIN_NAME`/`ADMIN_PASSWORD` غير مُمرَّرة لخدمات laravel | البذر يفشل بصواب (حماية إنتاجية)، لكن لا سبيل لتزويدها | `docker-compose.release.yml` — إضافتها لمرساة `x-laravel-env` المشتركة |
| 4 | أحجام Docker الفارغة الجديدة تُركَّب بملكية root | php-fpm (يعمل بـwww-data) لا يقدر يكتب لـ`/app/storage` | مُسجَّل كتوصية تشغيل (`chown -R www-data:www-data` عند أول تشغيل) — لم يُعدَّل الـDockerfile |
| 5 | `buildUpdateAdapter`'s `exec: (args) => adapter.exec(args)` يُسقط `options` | `runBackupCommand` يفقد `{inherit:false}`، فيُطبع الناتج على الطرفية بدل التقاطه، فيفشل تحليل JSON رغم نجاح الأمر الحقيقي (`exit 0`) — **هذا وحده كان يُجهض كل تحديث موقَّع** | `control-center.mjs:413` — تمرير `options` كما هي |

العيب #5 هو الأخطر: بلا إصلاحه، **لا يمكن لأي تحديث موقَّع أن ينجح إطلاقًا**،
بغض النظر عن صحة أي شيء آخر. اكتُشف بمقارنة مخرجات `docker exec` المباشرة
(نظيفة) بمخرجات `adapter.exec` عبر مسار التحديث (فارغة رغم `exit 0`) —
تتبُّع دقيق للسبب، لا تخمين.

## سلسلة الأدلة الفعلية

1. **تثبيت:** `install --config=` نجح — 7 خدمات healthy، `/api/v1/health`
   أعاد `ok:true`. digests حقيقية (postgres/redis من Docker Hub الفعلي عبر
   `docker pull` مباشر، laravel/next من سجل محلي فعلي `registry:2` دُفعت
   إليه صور مبنية محليًا فعليًا ثم استُبدلت بمراجع محلية بنفس الـdigest
   الحقيقي — تقنية مطابقة لآلية `offline-bundle` المعتمدة في المشروع نفسه،
   موثَّقة في `docker-compose.release.yml`).
2. **تحديث:** `update` (`1.0.0-test1 → 1.0.0-test2`) نجح بعد إصلاح العيب #5 —
   نسخة احتياطية حقيقية، فحص صحة حقيقي، فحص smoke بدور مصادَق حقيقي
   (تسجيل دخول فعلي بحساب المشرف المزروع)، تبديل حاويات كامل.
3. **آلية الأمان (auto-rollback):** قبل نجاح المحاولة الأخيرة، فشلت 3
   محاولات تحديث بأسباب مختلفة (فحص صحة بلا إعادة محاولة، غياب رمز smoke،
   `APP_BASE_URL` لا يزال `https://example.com` الافتراضي) — **وفي كل
   مرة، تراجع النظام تلقائيًا وبأمان** (`restoredPreviousRelease:true`) دون
   أي تدخل يدوي. هذا إثبات إيجابي قوي: شبكة الأمان تعمل كما صُمِّمت.
4. **تراجع صريح:** `rollback` (`1.0.0-test2 → 1.0.0-test1`) نجح — فحص صحة
   حقيقي، عودة كاملة. المانفست النهائي في
   [`final-manifest.json`](final-manifest.json).

## ملاحظة تشغيلية غير مُصلَحة (لا تحجب الإغلاق)

فحص الصحة بعد التبديل (`updateHealthCheck`) يجري **مرة واحدة فقط بمهلة 5
ثوانٍ، بلا إعادة محاولة** — عرضة لفشل عابر عند إقلاع بارد. لم يُعدَّل عمدًا
تحت ضغط الوقت لتفادي تغيير سلوك إنتاجي بلا اختبار كافٍ. توصية للمستقبل:
حلقة إعادة محاولة قصيرة (مثال: 3 محاولات كل 5 ثوانٍ) قبل اعتبار التحديث
فاشلًا.

## التنظيف

`docker compose down -v` + إزالة الشبكة/الأحجام + حذف صور السجل المحلي +
إزالة الـworktree — تحقّق `docker ps -a`/`docker volume ls` بعد التفكيك
يؤكد صفر أثر. المكدس الحي (`infra-*-1`) لم يتأثر طوال العملية بأكملها.
