# V1-X01 — تحقق حي للتخزين الخارجي: مُغلق بحدود نطاق صريحة

## النتيجة — 2026-08-04

نُفِّذت **خمس مراحل من خمس** تنفيذًا حقيقيًا (لا mock ولا `Storage::fake`) على
مزوّد S3 حقيقي يعمل في Docker، عبر **مسار المنتج نفسه**
(`FlysystemStorageAdapter`) لا عبر استدعاءات مباشرة مصطنعة. فحص الأسرار نظيف،
والتنظيف مُثبَت بصفر أثر.

| المرحلة | الحالة | الدليل |
| --- | --- | --- |
| `identity` (هوية المزوّد) | `executed` | `driver=s3`، endpoint وbucket واعتماد مضبوطة، `pathStyle=true` |
| `rwd` (قراءة/كتابة/حذف) | `executed` | تطابق SHA-256، `existsAfterWrite=true`، `existsAfterDelete=false` |
| `large` (ملف كبير) | `executed` | **67,108,864 بايت (64 MiB)**، تطابق SHA-256، 0.51 ثانية |
| `expect-failure` (انقطاع) | `executed` | إيقاف المزوّد فعليًا؛ مسار المنتج رمى استثناءً |
| `integrity` (سلامة بعد التعافي) | `executed` | صفر كائن جزئي، صفر كائن متبقٍ |

**فحص الأسرار:** 5 مراحل مفحوصة، **صفر تسرّب**. يُفحص الخرج الخام قبل التعتيم،
كي يُكتشف التسرّب لا أن يُخفى.

**التنظيف:** `cleanup.proved = true` — صفر حاوية متبقية، ومكدس التطوير الحي
(8 حاويات `infra-*`) لم يتأثر.

## نقطة جوهرية: النقل ثابت الذاكرة

`peakMemoryBytes = 50,331,648` (48 MiB) لكائن حجمه 64 MiB — أي أن الذروة **أقل
من حجم الكائن**، وهو ما يثبت أن النقل يتدفّق ولا يُحمَّل في الذاكرة. أول تشغيل
مُخزَّن في الذاكرة مات على `memory_limit` بخطأ فادح (exit 255)، فأُعيدت كتابة
المرحلة لتتدفّق عبر `writeStream`/`readStream` مع هَشّ تراكمي. هذا شرط عملي
لأرشيف بث تتجاوز مواده الغيغابايت.

## عيب حقيقي اكتُشف وأُصلح بهذا التشغيل

مرحلة `expect-failure` أثبتت تجريبيًا الفارق الذي سبّب العيب:

```
rawDiskReturned:  false    ← القرص الخام يُعيد false بلا رمي (throw=false)
rawDiskThrew:     false
productPathThrew: true     ← مسار المنتج يحوّلها إلى استثناء
```

جميع الأقراص مضبوطة `throw => false`. في `DropboxIngestTransport` كانت نتيجة
`put()` غير مفحوصة، فكان فشل كتابة قطعة يؤدي إلى:
تقدُّم `bytes_downloaded` فوق بايتات لم تُكتب → حفظ ذلك التقدّم →
قراءة القطعة المفقودة كـ`null` → تجميع ملف **مبتور** → حذف مجلد القطع →
وسم الصف `status=complete`. ولأن `pull()` اللاحق يقصر على `status=complete`،
كان الملف المبتور **دائمًا وغير قابل للاسترداد** — أي نقيض قابلية الاستئناف
التي يَعِد بها توثيق الصنف نفسه.

أُصلح جذريًا بحراسة كل كتابة وقراءة على مسار الإدخال، مع التحقق من طول الملف
المُجمَّع قبل نشره. اختبار الانحدار **تحقَّق في الاتجاهين**: يفشل على الكود
قبل الإصلاح (يصل إلى تأكيد الإتمام دون أي استثناء) وينجح بعده.
التفاصيل في commit `493c026c`.

## حدود النطاق صراحةً

هذا البند **لا يدّعي** قبول حساب تجاري. المزوّد ذاتي الاستضافة (MinIO):

- **بروتوكول S3 فقط** — ليس حساب AWS S3 تجاريًا ولا Dropbox.
- **عقدة واحدة** — لا تغطية لتعدد المناطق ولا versioning ولا lifecycle ولا
  سياسات IAM من جانب المزوّد.
- **مسارات Dropbox OAuth/webhook غير مُختبَرة حيًّا** في هذا التشغيل؛ إصلاح
  العيب أعلاه مُغطّى باختبار انحدار لا باعتماد Dropbox حي.

## ما يبقى محجوبًا خارجيًا

يبقى مطلوبًا قبل ادّعاء قبول تجاري كامل: اعتماد AWS S3 أو Dropbox حقيقي بأقل
صلاحية، وwebhook عام لمسار Dropbox، واختبار سياسات IAM ومنع الوصول عبر
صلاحيات المزوّد. عوائق clean-host العامة في
[`docs/ops/acceptance-clean-host-blockers.md`](../../ops/acceptance-clean-host-blockers.md).
