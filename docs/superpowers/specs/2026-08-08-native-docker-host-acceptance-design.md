# اعتماد Native عبر Docker والجهاز المضيف

## الهدف

إغلاق فجوتي تشغيل Native المكتشفتين، ثم اعتماد قبول Windows Native على جهاز
Windows المضيف وLinux Native داخل حاوية Docker تعمل بـsystemd. يكون هذا هو
معيار القبول الرسمي للمستودع لترقية حالتي `windows-native` و`linux-native`
من `planned` إلى `supported`.

## حدود النطاق

- يبقى Docker مسار تشغيل منتج مستقل؛ لا يحل محل حزمة Native.
- يثبت Windows Native على الجهاز المضيف للتجربة فقط، باستخدام مجلد اختبار
  صريح وخدمات مملوكة بالـmanifest، ثم يُزال ويُتحقق من عدم بقاء خدمات أو ملفات.
- يثبت Linux Native في حاوية Debian مزودة بـsystemd وcgroup حقيقيين، مع
  PostgreSQL وRedis خارجيين داخل شبكة Docker معزولة.
- لا يتضمن النطاق PostgreSQL أو Redis محليين مُدارين؛ Native يستخدم endpoints
  خارجية كما يحدد عقد المنصات الحالي.

## التصميم

### 1. تهيئة التطبيق على Linux

يُضاف مولد إعداد Linux مستقل يكتب، داخل جذر تثبيت الحزمة، الملفات التي تعتمد
عليها الخدمات: `.env` و`Caddyfile` و`php-fpm.conf`. يطابق مدخلاته وسياسته مولد
Windows القائم، لكنه يستخدم مسارات وأوامر Linux ولا يكتب خارج جذر التثبيت.
يصبح `app-configured` خطوة صريحة وقابلة للاستئناف بين إعداد مجلدات التطبيق
وتشغيل وحدات systemd.

### 2. إزالة Native مشتركة

يصبح أمر `uninstall` موزعاً حسب نمط التثبيت. لمسار Native يستدعي adapter
المنصة لإيقاف الوحدات وإلغاء تسجيلها، ثم يزيل فقط الملفات والخدمات المذكورة في
installation manifest. لا يزيل PostgreSQL أو Redis الخارجيين، ولا يمس مساراً
لا يثبت الـmanifest ملكيته.

### 3. قبول Windows على المضيف

يُبنى bundle من الرتبانات المثبتة، ويُثبت في جذر اختبار مخصص مع PostgreSQL وRedis
خارجيين. يتحقق الاختبار من استجابة التطبيق والخدمات الست، ثم ينفذ إزالة Native
ويثبت عدم وجود الخدمات وبقايا جذر التثبيت. تحفظ الأدلة المنزوعة الأسرار في
`docs/evidence/v1-210d-native/`.

### 4. قبول Linux في Docker

يعمل الاختبار في حاوية Debian مع systemd وcgroup حقيقيين. يكرر دورة install →
health → uninstall مع endpoints خارجية. تحفظ النتائج في
`docs/evidence/v1-211d-native/` وتذكر صراحة أن بيئة القبول هي Docker/systemd.

### 5. مصدر الحقيقة التوثيقي

يُحدَّث `infra/platform/compatibility.v1.json` بعد نجاح القبولين فقط. تُراجع
خطتا Windows وLinux، وخطة V1 العامة، و`CHANGELOG.md` بحيث تعرض الحالة نفسها
ولا تشير إلى `TASKS.md` غير الموجود. يكون `CHANGELOG.md` سجل المنجزات، وخطط
Native هي سجل المتبقي وخطوات القبول.

## الفشل والسلامة

- أي فشل في health أو uninstall يمنع ترقية حالة `supported`.
- يحتفظ الاختبار بسجل أوامر وحالة الخدمات وchecksums دون أسرار أو قيم اتصال.
- تتم إزالة Windows داخل كتلة تنظيف حتى عند فشل تحقق لاحق؛ إن تعذرت الإزالة
  تسجل الأدلة الحالة وتبقى المنصة غير مدعومة.
- لا يُنفذ update أو rollback في هذه الدفعة لأن adapter Native لا يملكهما بعد؛
  يسجل ذلك كقيد دعم صريح بدلاً من الادعاء بإتمامهما.

## التحقق

1. اختبارات وحدات red/green لمولد إعداد Linux ولموزع uninstall Native.
2. مجموعة اختبارات Control Center كاملة.
3. بناء bundle لكل منصة والتحقق من `SHA256SUMS`.
4. قبول Windows المضيف وLinux Docker/systemd مع تنظيف مثبت.
5. فحص عقد المنصات وبوابة release-readiness بعد تحديث الأدلة.

## معايير القبول

- لا تعمل خدمات Linux Native في حلقة تعطل بسبب ملفات إعداد مفقودة.
- يزيل `uninstall --mode=native` الخدمات والملفات المملوكة فقط على المنصتين.
- توجد أدلة قابلة للمراجعة للدورتين المحددتين أعلاه.
- يعرض العقد والسجل والخطط الحالة والقيود نفسها.
