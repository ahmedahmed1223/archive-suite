# Archive Suite v1.1.0 Public Release Design

## Outcome

Publish `v1.1.0` as a General Availability release of the canonical Laravel and
Next.js product. The release includes supported Docker, Windows Native, and
Linux Native distributions, documented Whisper transcription, bilingual public
documentation, reproducible release evidence, and a GitHub Release page whose
downloadable assets are produced only by the release workflow.

## Scope

The release covers `archive-next/`, `archive-laravel/`, the public API contract,
the Docker deployment under `infra/`, the Windows and Linux Native bundle
builders under `scripts/control-center/`, release automation, and public Arabic
and English documentation. The legacy `archive-app/` and `archive-server/`
implementations are excluded.

No new product feature is part of this release-preparation change. Public API
behavior must remain backward compatible within API v1. If verification exposes
a product defect, it is fixed in the canonical implementation with a focused
regression test before release work continues.

## Release identity and support declaration

- The product version is `1.1.0`; the Git tag and release title are `v1.1.0`.
- Docker on Windows and Linux, Windows Native, and Linux Native are supported
  deployment targets.
- Native support means the published packages install and operate the canonical
  Laravel and Next.js services without Docker on the target host.
- Windows Native supports Windows 10 and 11. Linux Native requires `systemd`.
- PostgreSQL may be managed locally or supplied by the operator. Redis remains
  optional according to the compatibility contract.
- Whisper transcription is supported through the product's canonical
  `whisper-ctranslate2` integration. CPU is the portable baseline; GPU operation
  is supported only where the documented CUDA/runtime prerequisites and the
  release acceptance gate are satisfied.
- Speaker diarization remains conditional on its documented provider token and
  dependencies and must not be implied by the base Whisper declaration.

## Published artifacts

The GitHub Release workflow publishes all of the following from the tagged
commit, or publishes nothing:

1. Immutable Next.js and Laravel container images in GHCR, referenced by digest.
2. A verified Docker offline bundle.
3. A versioned Windows Native package and its installation manifest.
4. A versioned Linux Native package and its installation manifest.
5. Native acceptance evidence for both platforms.
6. Image SBOMs and dependency-license inventories.
7. `release-images.txt`, `SHA256SUMS`, and signature/provenance evidence needed
   to verify every downloadable artifact.

Artifact names include `v1.1.0` and the target platform. Checksums are generated
after the final files are assembled, verified in CI, and attached beside them.
The workflow must not reuse untracked local files or artifacts from an earlier
run.

## Release pipeline

The existing tag-driven workflow remains the only publication entry point. It
is extended into these gated stages:

1. Validate tag/version coherence and run `pnpm run release:verify`.
2. Build and test the canonical Docker images, scan them, attach SBOM and
   provenance, and sign immutable digests.
3. Build Windows Native and Linux Native packages in platform-appropriate jobs.
4. Run the repository's Native acceptance runner against each produced package
   and retain machine-readable evidence.
5. Exercise the canonical Whisper executable and configuration using a bounded
   transcription smoke fixture. A GPU-specific gate verifies the declared GPU
   path without making GPU hardware a requirement for CPU installations.
6. Assemble checksums, license inventories, manifests, evidence, and offline
   assets.
7. Create the GitHub Release only after every required job succeeds.

Jobs upload intermediate workflow artifacts so the final publication job can
assemble one atomic release. GitHub environment permissions stay least
privilege: verification jobs are read-only; only the final image and release
jobs receive package or content write permissions.

## Documentation and release page

Arabic and English documentation must agree on the supported platforms,
requirements, installation paths, backup-first upgrade procedure, Whisper CPU
and GPU configuration, model storage expectations, diagnostics, rollback, and
support window. The following public surfaces are updated together:

- `README.md` and `README.ar.md`
- `INSTALL.md` and `INSTALL.ar.md`
- `DEPLOYMENT.md` and `DEPLOYMENT.ar.md`
- Native installation and support guides under `docs/`
- platform parity and versioning documents
- `docs/release-notes/v1.1.0.md` and its Arabic edition
- the in-product “What’s new” content

The release page leads with user outcomes, then lists supported installation
choices, upgrade precautions, Whisper requirements, downloadable artifacts,
checksum/signature verification, known limitations, and links to the maintained
documentation. It must not retain the obsolete statement that Native support is
`planned`.

## Verification and acceptance

Release readiness requires fresh successful evidence for:

- public documentation and link consistency;
- OpenAPI/client/server contract consistency;
- Next.js type checking, unit tests, production build, and live Laravel/Next.js
  integration;
- the Laravel test suite;
- repository security baseline and dependency audit;
- Docker configuration, image build, image smoke tests, vulnerability scans,
  signing, and offline-bundle rehearsal;
- Windows and Linux Native build, checksum verification, clean-install
  acceptance, health checks, service lifecycle, update/rollback behavior,
  backup/restore safety, and uninstall cleanup limited to owned paths;
- Whisper CPU smoke transcription and the declared GPU acceptance path;
- reproducibility, license policy, SBOM generation, and release-asset checksum
  verification.

The release is blocked by any failing required gate, missing evidence, stale
support statement, unresolved critical vulnerability with an available fix, or
version mismatch. A failed workflow does not create or partially update the
public GitHub Release.

## Publication and rollback

Before publication, the local branch must be reconciled with the remote without
rewriting public history, the final commit must pass the complete release gate,
and the user must explicitly approve the external push and tag creation.
Pushing `v1.1.0` triggers publication. The workflow is monitored until every
asset and image digest is available and its checksum/signature verification has
passed.

If publication fails before release creation, fix the cause and create a new
commit; never move an already published tag without explicit destructive-action
approval. If a faulty release becomes public, preserve its evidence, mark it
appropriately, publish corrective guidance, and issue a patch release rather
than silently replacing artifacts.

## Success criteria

`v1.1.0` is complete when the public GitHub Release exists, all declared assets
are downloadable and verifiable, GHCR images resolve by the recorded digests,
Arabic and English documentation describe the same supported product, clean
Windows and Linux Native acceptance evidence is attached, Docker and offline
paths pass, Whisper's documented paths pass their gates, and no required release
check remains failing or pending.
